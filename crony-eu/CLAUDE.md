# CLAUDE.md

Read this file at the start of every session. It overrides anything a task description implies. If a task seems to need breaking a rule here, stop and ask the maintainer.

## What exists today

**Documentation. No code.** There is no `crony-eu/src/`, no `crony-eu/tests/`,
no `pyproject.toml` of this project's own and no `crony` command. Everything
below describing modules, tables, commands and outputs is a **specification
written before the code**, which is the point of it, and is not a description of
something you can run.

Session 0 in `crony-eu/docs/work-order-phase-1.md` is what builds the first of
it. A document here that reads as though a module exists is a bug worth fixing
on its own, because the reader who believes it wastes an afternoon.

## Where this sits

This directory is one project inside one repository, and the repository is being
handed over to it. The canonical scope is [`scope.md`](../scope.md) at the root;

numbered from 0001, and this project's stay under `crony-eu/docs/adr/`, also
numbered from 0001. A citation says which series it means.

Paths in this directory's documents are written **from the repository root**
(`crony-eu/docs/sources/france.md`, not `docs/sources/france.md`), so that
`tests/test_docs.py` can check them. Data directory paths are written
`$CRONY_DATA_DIR/raw/`, never a bare one, because a bare one reads like a
directory in the repository and the first rule here is that data never is.

## What this repository is

`crony-eu` (working name) is a local-first pipeline that links elected officials, companies and public contracts using official open data. It follows the idea of Sophie E. Hill's My Little Crony (https://github.com/sophieehill/my-little-crony, MIT), which mapped links between UK politicians and firms that won pandemic contracts. Her network was built by hand from published journalism. Here, public registries propose candidate links, and a person confirms each one before it can appear in any output.

The output is a case packet: a standalone HTML network, the edge list, and the source behind every edge. The maintainer (Felipe) shows packets to journalists and research partners from his own machine. This repository publishes nothing and holds no data.

Pilot country: France. Phase 1 covers communes only, one département at a time. See `crony-eu/docs/work-order-phase-1.md`.

## Hard constraints

1. No data in git. Everything downloaded or derived lives under `$CRONY_DATA_DIR`, an absolute path outside the repository, on an encrypted volume. The repository holds code, docs, and fixtures generated by Python code. No real person's name or record goes into code, tests, docs, screenshots, commit messages, issues or PR text, not even with the name changed. Aggregate counts ("412 candidate matches in the slice") are fine in docs; names and personal identifiers are not. `crony-eu/scripts/check_no_data.py` runs as a pre-commit hook and in CI.

2. Provenance on everything that reaches an export. Every node attribute and every edge in an export carries the source dataset, the most specific source URL available, and the retrieval timestamp. No provenance, no export.

3. Candidate matches are not facts. Matching writes candidates to the judgments table with status `pending`. Only a `confirmed` judgment, set by a person through `crony review`, can put a person-to-company edge into an export. Flags may run on candidates for triage; every such output row says `unconfirmed`.

4. Deterministic runs. Same inputs and same code give byte-identical outputs. Sort before writing. Fix every seed, including the vis-network layout seed. The only timestamps inside data are `retrieved_at` values recorded at fetch time. Transform stages make no network calls.

5. Rules, not models. Matching, flags and scores use structured fields and written rules. No machine learning, embeddings or LLM calls anywhere in the pipeline.

6. Listed sources only. A source is usable only after it has a section in `crony-eu/docs/sources/<country>.md` approved by the maintainer. Respect licences, rate limits and terms of use. Use official APIs and bulk files; never scrape web pages or commercial aggregators.

7. Two French legal rules, enforced in code.
   - Parliamentarians' asset declarations (déclarations de situation patrimoniale) are never ingested, from any source, unless the parliamentarian published the declaration themselves. Code électoral art. LO 135-2 fines any publication or disclosure of them (EUR 45,000), and showing one to a journalist would count as disclosure. The usual way they sneak in is secondhand: an article or a leak quoting a declaration someone consulted in a prefecture. Ministers' asset declarations, which HATVP publishes online, are allowed.
   - Companies that are not publicly diffusible (INSEE/INPI non-diffusion status) never appear in exports. INPI's documentation says reusers may not redistribute them even though the registry shows them. If a match lands on one, list it for the maintainer and stop there.

8. Every flag has a spec before its output is used. `crony-eu/docs/flags/<ID>-<name>.md` states the hypothesis, the definition, the innocent explanations, the measured base rate (with the query that measured it) and what a journalist has to verify. Until the base rate is measured, the flag's output is marked `uncalibrated` and cannot enter a case packet.

9. Dates must overlap, and phase 1 has to be able to tell. A hit needs the mandate, the officer role and the contract notification date to overlap. Missing dates give `unknown`, never `true`, and **an `unknown` overlap cannot enter a case packet**. It can be counted, reported and reviewed, but not handed to a journalist as a link in time.

   This is why officer role history is phase 1 work and not phase 2. The first bundle put role dates in phase 2 while phase 1's only flag needed them, which would have produced a phase 1 whose every hit was ineligible for the output phase 1 exists to build. Session 3 measures whether a French source carries dated roles before anything downstream is written, and stops if none does.

10. Offline outputs. The HTML output loads nothing from the network: JavaScript and CSS are inlined, and a Content-Security-Policy meta tag forbids external requests. Links to sources are plain anchors the reader chooses to click.

    Offline is a property of the file, not a privacy control. A packet handed to a journalist has left this machine as completely as a website would have, and everything in it is disclosed. Running locally decides *who* discloses; it decides nothing about *what*.

11. An export refuses; it does not filter afterwards. Nothing reaches `$CRONY_DATA_DIR/cases/` unless every one of these holds, and the packet's status block says so for each:

    - the company may be redistributed (INSEE/INPI non-diffusion excludes it outright, and a match landing on one is listed for the maintainer and goes no further)
    - every person-to-company edge carries a `confirmed` judgment
    - `mandate_overlap` and `role_overlap` are both `true`
    - the flag's base rate has been measured, so it is not `uncalibrated`
    - the evidence copied in is only the source records the packet's own edges cite. Not the slice, not the neighbouring rows, not the officer list the match came out of

    A packet records the judgment ids and the rule id it was built under. When a judgment behind a packet later becomes `rejected` or `ambiguous`, that packet is **invalid**: the maintainer is told which packets relied on it and withdraws them from anyone who has a copy. Judgments are append-only so this question stays answerable, and a packet that cannot name its judgments cannot be checked and should never have been built.

12. An aggregate is not automatically person-free. Counting instead of naming protects nobody when the count is over four people. "The share of local contract value going to companies with a councillor on the board" is safe for a département and identifying for a commune of four hundred with one supplier. So an aggregate may leave the machine only with its cell sizes beside it, computed over a population large enough that no cell points at anyone, and after the maintainer has looked at the small cells. Below that it is a case packet or it is nothing.

13. Agent sessions don't read personal values. When a Claude Code session inspects real data, it prints schemas, row counts, null rates and pattern summaries (string lengths, character classes, date ranges), never names, birth dates or addresses. Looking at real records is the maintainer's job, in `crony review`, outside the agent.

## Stop and ask the maintainer when

- a task needs a source that has no approved section in `crony-eu/docs/sources/`
- real personal data would end up inside the repository tree, including logs, caches and notebooks
- anything touches asset declarations, health, religion, sexuality, criminal records or minors
- a source's licence, terms or rate limit are unclear
- a constraint above seems to block the task
- a result looks like a real story. Report the case id and nothing else; don't write it up.

## Stack

- Python 3.12+, uv (commit `uv.lock`), src layout, package `crony_eu`, CLI entry point `crony`
- DuckDB for transforms; Parquet with zstd compression between stages
- httpx for HTTP, with retries (exponential backoff with jitter) and a per-source rate limiter
- typer for the CLI; rich for the review screen
- jinja2 for the HTML template; vis-network vendored as its standalone UMD build, version pinned, licence file alongside
- pytest, hypothesis (property tests for normalisation), ruff (lint and format), mypy (strict on `crony-eu/src/`)
- pre-commit with local hooks only (see `crony-eu/.pre-commit-config.yaml`)
- License: AGPL-3.0-or-later; SPDX header in every source file. **The repository's `LICENSE` is the plain AGPL-3.0 text and says nothing about "or later".** The two statements have to be reconciled before this project's first source file is written, and reconciling them is a licensing change affecting every existing contributor's DCO sign-off, so it gets its own ADR rather than an edit here ([ADR-0014](../docs/adr/0014-replace-serenata-with-crony.md))
- No `followthemoney` dependency in phase 1 (ADR-0002). Tables carry FtM schema names in an `ftm_schema` column.

Name normalisation uses the standard library (`unicodedata`), not `unidecode` (licence and determinism).

## Data directory ($CRONY_DATA_DIR)

```
raw/<source>/<YYYY-MM-DD>/        # bytes exactly as downloaded + manifest.json
staged/<source>/<YYYY-MM-DD>/     # typed Parquet
staged/_reports/                  # data-quality reports (aggregates)
matched/judgments.parquet         # append-only log; latest row per judgment_id wins
flags/<FLAG_ID>/<run_id>/         # flag outputs
cases/<case_id>/                  # network.html, nodes.csv, edges.csv, sources.md, evidence/
logs/
```

`manifest.json` records, per file: url, sha256, bytes, retrieved_at (UTC, ISO 8601), licence, HTTP status. `$CRONY_DATA_DIR/raw/` is never modified after writing. Each stage reads only the stage before it. A `run_id` is a hash of the input manifests plus the package version.

## Export contract

`nodes.csv`

| column | meaning |
|---|---|
| node_id | stable id (hash of kind + source key) |
| kind | Person, Company, PublicBody |
| ftm_schema | FtM schema name (same values as kind in phase 1) |
| label | display label |
| attributes_json | extra attributes, each with its source |
| source_refs | ids of the source records |

`edges.csv`

| column | meaning |
|---|---|
| edge_id | stable id |
| source_node, target_node | node ids |
| kind | mandate, officer, contract, declared_interest, reported |
| ftm_schema | Membership, Directorship, ContractAward, Ownership, UnknownLink |
| amount_eur | contract amount, empty otherwise |
| start_date, end_date | ISO 8601 or empty |
| evidence_status | registry, confirmed_match, reported |
| source_dataset, source_url, retrieved_at | provenance |
| judgment_id | set for confirmed_match edges; the handle that makes a packet withdrawable when the judgment changes |
| rule_id | the matching rule the judgment was made under, so a rule change does not silently revalue old packets |

`reported` edges come from published journalism, entered by hand with the article URL, and are drawn dashed. None exist in phase 1.

A case packet opens with a status block: flag id, calibration date, judgment status, the rule id, the run id, every overlap and its value, and the verification checklist copied from the flag spec. Under constraint 11 a packet only exists when every overlap is `true`, so the block reads as a record of what was checked rather than a list of caveats. If it ever shows an `unknown`, the packet was built by something that bypassed the export gate and should not be trusted.

## Matching (France, phase 1)

Rule id `FR-NAME-BIRTHYM-v1` (ADR-0003):

- normalise: NFKD, drop combining marks, uppercase, turn apostrophes and hyphens into spaces, keep A-Z and spaces, collapse spaces
- surname variants: the élu's `Nom de l'élu`; the officer's birth name and, when present, usage name
- given name: the first given name, with hyphenated compounds kept together (JEAN-PIERRE -> JEANPIERRE)
- birth: year and month (YYYY-MM)
- a candidate exists when any surname variant, the given name and the birth month all match exactly
- `key_collision` is set when one key maps to more than one élu or more than one distinct officer record
- the review screen shows territory hints (the company's address against the élu's commune), but a hint never confirms a match on its own

Changing the rule means a new rule id, never an edit in place.

## HTML output

- one file, JS and CSS inlined, CSP meta tag: `default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data:`
- fixed `layout.randomSeed`; physics runs to stabilisation, then turns off
- node colour and shape by kind; edge colour by kind; edge width from log10 of the amount; `reported` edges dashed
- every string is escaped before it reaches the template; tooltips are built as DOM text nodes, never `innerHTML` with data in it
- a legend, and a sources panel listing every edge's source link and retrieval date

`crony doctor` checks that the data dir is set, absolute, outside the repo and writable; that the git tree has no data files; that templates carry the CSP tag; and that the vendored asset's hash matches `VERSION`.

## Conventions

- type hints everywhere; mypy strict on `crony-eu/src/`
- each source module exposes `fetch()`, `stage()` and a `SCHEMA` dict (column -> DuckDB type) that a test pins
- logs go to `$CRONY_DATA_DIR/logs/` only; INFO-level messages carry ids and counts, never names
- tests use generated fixtures; tests that hit the network are marked `live`, skipped by default, and never write outside a temp dir
- an ADR records every decision that changes this file

## Definition of done for a session

- `uv run pytest` green
- `uv run ruff check .` and `uv run ruff format --check .` clean
- `uv run mypy src` clean
- `uv run python scripts/check_no_data.py --all` clean
- docs updated: observed source schemas, flag spec, a new ADR if a decision changed
- the session's box ticked in `crony-eu/docs/work-order-phase-1.md`, with one line on what changed

## Writing style (docs, comments, commit messages, CLI text)

Plain words, specific facts, varied sentence length. Don't use "delve", "leverage", "robust", "seamless", "crucial", "It's not X, it's Y" constructions, questions answered in the next sentence, bold-first bullets, emoji, em dashes (use commas or parentheses) or unicode arrows (write ->). Commit messages: imperative mood, what changed and why.
